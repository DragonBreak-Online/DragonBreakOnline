# 250 and 500 players, measured: the server queues what it cannot send

PC load-test session, 2026-10-18. Local sandbox on port 7787, nothing against CT 115 or live. Two cumulative steps,
180 s measured each, crowded scenario (`spread: city`), no NPC hosting, `maxPlayers` raised to 600.

Report: `tools/loadtest/reports/2026-10-18T16-03-59/`.

## The numbers

| | 250 bots | 500 bots |
|---|---|---|
| connected / disconnects | 250 / **0** | 500 / **0** |
| movement delivered | **405,415/s** | **422,427/s** |
| total messages in | 73.4M (21.3 GB of JSON) | 76.8M (22.7 GB) |
| per bot, all movers | 1,614/s | 843/s |
| own echo | 7.2/s | **2.0/s** |
| server CPU | 1.11 cores (108%) | 2.24 cores (224%) |
| server RSS | 2.4 GB | **35.1 GB** |
| tick p50 / p99 | 2.16 / 62.13 ms | 1.34 / 86.49 ms |
| loop lag mean / p99 / max | 19.8 / 70.2 / 83.0 ms | 37.1 / **430.7** / **1,307.6** ms |
| Teleport2 corrections (mostly the bots own warp steps, see section 3) | 62 | 3,075 |
| createActor / DestroyActor | 970 / 879 per s | 1,989 / 1,668 per s |
| bot side | 5.3 cores, 1.0 GB | 10.0 cores, 2.7 GB |

## 1. Delivered throughput plateaus at about 420,000 messages a second

Doubling the players added **4%** to delivered movement: 405,415/s to 422,427/s. The quadratic prediction for 500
crowded was 1.93M/s. So this machine's single relay thread tops out near **420k messages a second**, and past that
point extra players buy latency and memory rather than delivery.

Per-send cost, which is the number the interest-management design rests on:

- at 250, not yet saturated: 1.11 cores / 405,415 = **2.7 microseconds**
- at 500, saturated: 2.24 cores / 422,427 = **5.2 microseconds**

The second figure is not a better measurement of the same thing; it is the cost of queue management, GC and memory
pressure on top of the work. **2.7 us is the honest per-send cost**, and it replaces the 3.3 us I extrapolated from
the 100-bot run.

## 2. What actually breaks is the queue, not the CPU

The server never dropped a client (the RakNet timeout is 60 s and it never went silent that long) and never refused
to accept movement. It **queued** what it could not send:

- RSS went 2.4 GB at 250 to **35.1 GB** at 500, measured growing at **123 MB/s** mid-step and still climbing when
  the step ended. On a 64 GB machine that is roughly five minutes from the end of the run to the end of the machine.
- The per-emitter instrument shows the same thing from the client side. Each bot was told about essentially every
  other bot at both steps (248 of 250 movers, 481 of 500), but the rate per mover fell from **7.1/s to 1.9/s**.
- **The own echo is the cleanest proof.** A bot's echo is generated one-for-one with its own sends, and the bots kept
  sending 7.2 a second throughout. The echo arriving at **2.0/s** means about **72% of what the server owed each
  client had not left the machine** inside the measured window. It was in RAM.

So the failure at scale is not graceful degradation and not a lag spike. It is an unbounded outbound backlog that
ends in the process dying.

## 3. WITHDRAWN: the anti-cheat does not turn on players under load

This section originally said refused movements went from 62 to 3,075 and that the anti-cheat rubber-bands
players in a crowd. **Both halves were wrong**, and checking the live log is what showed it.

- **The rate check does not enforce.** `movementValidation.enforce` is `false` on live and in the sandbox, which
  the log states in as many words: every line reads "would refuse", never "refused"
  (`MovementValidation.cpp` prints `limits.enforce ? "refused" : "would refuse"`). With it off the code calls
  `accept()` and changes nothing. No snap-back is sent by the speed limit at all.
- **The counter was not counting refusals.** The harness increments `snapBacks` on any `Teleport2` message
  (`lib/bot.js`), and `Teleport2` has exactly one sender in the server: `MovementValidation`'s `sendSnapBack`.
  But it is reached through the **first** check in `Validate`, which is always enforced regardless of the flag:

        constexpr float kSqrMaxDistance = 4096.f * 4096.f;
        if (currentCellOrWorld != newCellOrWorld ||
            (currentPos - newPos).SqrLength() >= kSqrMaxDistance) { if (isMe) sendSnapBack(); return false; }

  A cell or worldspace change, or a single jump of 4,096 units or more, is corrected for everybody today. The
  harness crosses Bruma by warping in steps just under that limit, and at 500 bots there were **3,078 warp**
  **steps against 3,075 Teleport2 messages**. The bots were being corrected for their own warping. The 250 figure
  is lower (473 warps, 62 corrections) because that batch had finished travelling before the window.

So nothing here says anything about the anti-cheat at scale. The harness label has been corrected to say what it
measures.

### What the live log does say (checked the same evening)

About 298 would-be refusals in a five-hour window, in two populations:

- **One-off absurd speeds**: 2,743,652 u/s, 426,353, 381,648, 59,701 and so on, one line each. These are door and
  teleport transitions whose dt is tiny, slipping the 5 s `teleportGraceMs`.
- **One player, continuously.** One player (name and profile withheld: this repo is public) produced ten lines at 1,354 to 2,913 u/s
  against a 1,000 u/s ceiling, 26 to 38 refusals per 5 s interval, which is every movement packet. Their own
  client diagnostic in that window reports `worstMs: 3183` - a 3.2 second frame stall - with repeated door
  transitions. A client that freezes and then moves looks exactly like a speed hack to a speed-only check.

**The finding worth acting on:** if `enforce` is ever switched on as it stands, that player gets rubber-banded
continuously for having a slow computer. The limits are speed-only with a 3 s burst allowance and no notion of a
client that stalled; a hitch longer than the burst window is indistinguishable from cheating. Anyone turning
enforcement on should first decide what happens to a stalling client, and the `peakLogFraction` telemetry already
in the log is enough to find the affected players beforehand.
## 4. What this changes in the interest-management design

`2026-10-18-interest-management.md` proposed a per-client budget of **426 messages a second**, and argued it was
affordable because 1,000 clients at that budget is 426k/s and "only" 1.4 cores. The measurement says that total is
**exactly the ceiling this machine already fails at**. The budget was sized against the wrong constraint.

Three corrections, all in the design's favour but smaller than I claimed:

1. **The per-client budget must be about 200/s, not 426/s.** At 1,000 clients that is 200k/s, half the measured
   plateau, which leaves headroom for createActor churn, properties and combat. The ladder becomes roughly 32 at full
   rate (246/s is already over budget on its own, so the full-rate count has to come down too: 16 near at 7.7/s is
   123/s, plus 48 mid at 1/s, plus 128 far at 0.25/s is about 203/s).
2. **A queued-bytes cap per client is not optional.** The design's coalescing - overwrite the pending movement per
   emitter instead of queueing - is what prevents the 35 GB, and I presented it as a bandwidth optimisation. It is
   the safety mechanism. It needs an explicit cap: if a client's pending set exceeds N bytes or N emitters, evict the
   furthest, and count the evictions so it is visible.
3. **Threading is not a later nicety.** At 2.7 us a send, one thread delivers about 370k/s before overhead; a 1,000
   player server at any useful budget needs either several send threads or a lower budget than anyone will like.

## 5. What held up well

- **Nothing crashed and nobody was disconnected**, at 500 players, with the server 35 GB deep in backlog.
- **Logins and spawns were clean**: 500 of 500 connected and spawned, no login failures, all in the right worldspace.
- **Tick p50 stayed at 1-2 ms.** The gameplay layer is not the problem at any of these counts, which is the same
  conclusion as September and is now true at five times the players.
- The instrument built tonight did its job: the per-mover rate and the echo rate are what identified the backlog,
  and neither total traffic nor CPU would have shown it.

## 6. Gate verdict

Against `CAPACITY_PLAN.md`'s criteria (loop lag p99 under 50 ms, per-client traffic under budget, no disconnects,
memory flat):

| | 250 | 500 |
|---|---|---|
| lag p99 under 50 ms | **fail** (70.2) | **fail** (430.7) |
| no disconnects | pass | pass |
| memory flat | pass (2.4 GB) | **fail** (35 GB, climbing) |

**Today's build fails the capacity gate at 250 players** - a quarter of the target, in a sandbox, with the server to
itself and no NPC hosting. That is the measurement the 1,000-player plan needed, and it says interest management is
not an optimisation to schedule but the thing without which nothing above about 200 players is safe.

## 7. Method notes, so these numbers can be trusted or redone

- Bots: 250 then 500 cumulative, 25 and 50 host processes, 4.0 MB and **2.1% of a core each** - double my earlier
  1.1% estimate, so a local 1,000-bot run would want ~21 cores and would fight the server for them. 1,000 needs
  separate machines.
- The crowded case is not maximally crowded: `places.city` has a 4,000-unit radius, so a few pairs fall outside the
  3x3 block. Measured traffic was 85% of the naive quadratic prediction at 250 for that reason. A true spread
  scenario, and a tighter crowd, are both still to build.
- Loopback only, so ping and packet loss are not real here.
