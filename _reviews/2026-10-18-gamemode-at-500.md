# The gameplay layer at 500 players: three timers, and the cost is a blocked loop rather than CPU

PC load-test session, 2026-10-18, for the leader's profiling task. Local sandbox only. Source read from
`origin/server` at `774f50fd` (this PC's checkout is 347 commits behind and was not used). No gamemode edited.

Measured from the gamemode's own `ticks (ms, last 60 s, N online)` lines, which already report runs, mean and max
per timer, in the windows of the 500-bot passes: `tools/loadtest/reports/2026-10-18T21-14-43` (relay on, 500),
`2026-10-18T20-41-25` (relay on, 250 and 500), `2026-10-18T21-20-13` and `20-27-06` (relay off), and the two
spread runs `20-50-26` and `20-36-07`. A `--cpu-prof` run was not needed: the per-timer instrumentation already
in the gamemode is finer than a profile would be for this question, because it attributes by timer rather than
by function, and the spread runs separate crowding from population better than any profile can.

## 1. The headline: all timers together cost 17.5% of a core

| | 250 crowded | 500 crowded | 250 spread |
|---|---|---|---|
| all timers | 99.1 ms/s | **175.1 ms/s (17.5% of a core)** | 71.1 ms/s |
| gamemode's own loop p99 | 82 ms | **641 ms** | 29 ms |
| relay off, same population | - | 186.8 ms/s, loop p99 537 ms | - |

So the gameplay layer is **not** short of CPU at 500, and the relay makes no difference to it (175 vs 187 ms/s is
inside the run-to-run spread). What it is short of is *uninterrupted* time. The loop p99 is 641 ms while the work
is 175 ms per second, which can only mean the work arrives in large synchronous lumps:

- one `npcGround` run a second, **75.5 ms** each
- one `debugSnap` every five seconds, **216 ms** each
- up to four `racialRegen` a second, **25.7 ms** each

A single second that contains a snapshot holds about **395 ms** of unbroken JavaScript. Nothing else - no packet,
no timer, no network read - runs during it. That is the 641 ms, and it is why cutting total CPU is the wrong
target: the fix is to make each run shorter or rarer, not to make the sum smaller.

## 2. Per timer, at both populations

Mean ms is per run; ms/s is the share of a second. Runs/60 s is what the window actually got, which matters
because the two biggest timers are being starved by the very stalls they cause.

| timer | period | 250: runs/60s | mean | 500: runs/60s | mean | max | ms/s at 500 | mean 250->500 |
|---|---|---|---|---|---|---|---|---|
| `npcGround` | 1 s | 58.7 | 18.7 | 49.3 | **75.5** | 108.9 | 62.1 | **4.03x** |
| `debugSnap` | 5 s | 11.7 | 56.0 | 11.3 | **216.0** | 280.6 | 40.8 | **3.85x** |
| `racialRegen` | 250 ms | 219.7 | 11.4 | 106.7 | **25.7** | 44.8 | 45.6 | 2.24x |
| `statDisplay` | ~2 s | 29.3 | 4.0 | 25.7 | 7.9 | 14.5 | 3.4 | 1.99x |
| `meet` | ~5 s | 11.7 | 4.3 | 11.5 | 12.3 | 16.4 | 2.4 | 2.84x |
| `journalStatsSample` | ~2 s | 29.3 | 2.2 | 25.7 | 4.7 | 10.6 | 2.0 | 2.13x |
| `beastForms` | 1 s | 58.3 | 1.1 | 49.2 | 2.4 | 10.5 | 2.0 | 2.20x |
| `watch` | 5 s | 11.7 | 4.0 | 11.3 | 9.3 | 15.4 | 1.8 | 2.32x |
| `loginSetup` | - | 125 | 1.3 | 87 | 1.3 | 10.3 | 1.8 | 1.00x |
| `playtest` | 5 s | 11.7 | 2.3 | 11.3 | 5.8 | 10.6 | 1.1 | 2.57x |
| `worldStats` | 60 s | 1 | 5.7 | 1 | 12.9 | 15.3 | 0.2 | 2.27x |

**Two timers lose runs as they slow down.** `npcGround` is a 1 s timer and got 49 runs in 60 s; `racialRegen` is a
250 ms timer and got 107 of its 240. So `racialRegen`'s true demand at 500 is **4 x 25.7 = 103 ms/s**, not the
45.6 ms/s observed - the observed figure is what a starved timer managed, and it will rise to 103 the moment the
loop frees up. Any plan that fixes `npcGround` and `debugSnap` must budget for `racialRegen` roughly doubling.

## 3. What scales with crowding, and what scales with players

The spread runs settle this. Same 250 players, same send rate, distributed instead of co-located:

| timer | crowded 250 | spread 250 | ratio | scales with |
|---|---|---|---|---|
| `npcGround` | 18.7 ms | 4.6 ms | **4.0x** | **crowding** |
| `debugSnap` | 56.0 ms | 13.2 ms | **4.2x** | **crowding** |
| `meet` | 4.3 ms | 2.9 ms | 1.5x | crowding, mildly |
| `racialRegen` | 11.4 ms | 10.3 ms | 1.1x | players |
| `statDisplay` | 4.0 ms | 4.0 ms | 1.0x | players |
| `journalStatsSample` | 2.2 ms | 2.1 ms | 1.1x | players |
| `watch` | 4.0 ms | 4.2 ms | 1.0x | players |

`npcGround` and `debugSnap` are the whole problem, they are both quadratic, and both are quadratic for the same
reason: each asks every player for its neighbours and then loops over them.

## 4. The code doing the work

**`npcGround`** (`npcground.js:171-196`). Every second:

    const skip = new Set(players);
    for (const p of players) {
      let near = [];
      try { near = mp.get(p, 'actorNeighbors') || []; } catch (e) { continue; }
      for (const id of near) { if (skip.has(id)) continue; skip.add(id); check(id, p, now); }
    }

`check()` runs at most once per distinct actor, which is correct and cheap. The cost is everything around it: at
500 co-located players this makes **500 `actorNeighbors` calls, each marshalling about 490 ids out of C++** -
roughly **245,000 ids a second**, every one of which is then discarded by `skip.has()` because the neighbour is a
player and was already in the set. Spread out, `actorNeighbors` returns 9 to 36 entries and the same loop costs
4.6 ms. The quadratic term is pure overhead: no NPC work is being done by it.

The same tick also carries a five-second block (`npcground.js:175-185`) that, for **every** player, reads
`worldOrCellDesc`, `pos`, looks up the terrain and **writes one log line per player**. At 500 that is 500 log
lines every 5 seconds, 100 a second of disk I/O, and it is diagnostic output only.

**`debugSnap`** (`debugsnap.js:33-56, 79-84`). Every 5 s, `snap()` calls `playerView(p)` for every online player,
and `playerView` does:

    let near = []; try { near = mp.get(p, 'actorNeighbors') || []; } catch (e) { near = []; }
    for (const id of near) {
      if (profileOf(id) >= 0) continue;
      ... five more mp.get calls per NPC ...
    }
    out.npcs.sort(...); out.npcs = out.npcs.slice(0, C.maxNpcs);

Same shape, worse constant: 500 x 490 = **245,000 `profileOf` calls per snapshot**, and in a player-only crowd
every one of them hits the `continue` and contributes nothing to the output. Note also that `maxNpcs` (40) is
applied **after** the full list is built and sorted, so on live - where the neighbours really are NPCs - it does
five `mp.get` calls each for up to 490 actors and then throws away all but 40. Then it pretty-prints
(`JSON.stringify(obj, null, 1)`) a 500-player structure and writes it.

**`racialRegen`** (`racial.js:458-511`, `TICK_MS` = 250 ms default). Strictly per-player: for each online actor,
`raceOf`, `mp.get(a, 'percentages')`, a downed check, then three stats through `regenFactor` and
`extraPerSecond`, and a write when a payout is due. **45.7 microseconds per player at 250, 51.3 at 500** - linear,
with a small constant. Nothing here is wrong; it is simply the most frequent per-player loop in the gamemode, and
at four runs a second it wants 10% of a core at 500 players.

**`meet`** (`gamemode.js:1178-1200`) is already grid-bucketed by one "say" reach, which is the right structure.
It degrades because a 500-player crowd inside a 4,000-unit radius falls into a handful of cells, so the 3x3 scan
becomes all-pairs: about 125,000 distance checks a run. No grid helps when the crowd is smaller than one cell;
only a per-tick pair budget or a longer period will.

## 5. Diagnostic rather than gameplay

Asked directly, in order of how much they would give back:

- **`debugSnap` is entirely diagnostic.** It exists to write `live.json` for the monitor and to serve `/bug`
  reports. 216 ms every 5 s at 500 players buys nothing a player can see. It is the single best candidate for a
  flag, a longer period, or a cap on how many players a snapshot covers. Its `logTailBytes` is 400,000, so each
  `/bug` also reads 400 KB of log.
- **`npcGround` is mixed.** Lifting an NPC that has sunk under the terrain is gameplay (`FIX_*`, and Nat's
  2026-09-25 rule that the server owns the ground). The five-second per-player terrain logging is diagnostic and
  can go behind a flag outright. The quadratic neighbour walk is neither - it is an implementation accident, and
  it would disappear if the tick iterated actors once instead of per player.
- **`loginWait`** is a 500 ms poll per logging-in player: 24,882 runs in 60 s at 250 and 34,152 at 500, which is
  **570 timer wakeups a second**. Each is 0.00 ms so it costs nothing measurable, but it is a lot of scheduling
  for a poll, and it is the one timer whose run count grows with login churn rather than population.
- **`worldStats`, `orphans`, `journalStatsSample`, `playerlog*`** are all bookkeeping, all small (0.05 to 2.0 ms/s
  at 500), and none worth touching.

## 6. One stall that has nothing to do with population

`gearStrip` and `sprStrip` run one sweep 60 s after load, and that first sweep is the **worst single stall in any
of these runs**: `gearStrip` mean 435.8 ms, **max 868.3 ms**; `sprStrip` mean 218.6 ms, max 433.8 ms. They are
identical at 250 crowded (435.8) and 250 spread (428.6), and at 500 they read 5.7 ms because the earlier step had
already done the work. So this is a fixed startup cost, not a scaling one - a nearly one-second freeze a minute
after every reload, independent of how many people are online. Worth a slice or an idle deferral on its own
merits, separately from the 500-player work.

## 7. What I would change first, if it were mine

Ordered by return, and all of it is the leader's to make:

1. **`debugSnap`: behind a flag, or every 30 s instead of 5.** Removes 216 ms every 5 s outright. Also move the
   `maxNpcs` cut before the `mp.get` calls rather than after the sort.
2. **`npcGround`: walk actors once, not once per player.** The tick already keeps a `skip` set of everything it
   has seen; building the union of neighbours first and then checking each actor once would turn 245,000
   marshalled ids a second into about 500. Put the five-second per-player terrain log behind the same debug flag.
3. **`racialRegen`: slice it.** It is correct and linear, but it is the floor on how short a stall can be at 500
   players, and it will roughly double once the loop frees up. Either halve the rate or process players in
   slices across ticks, as `statDisplay` already does with `STAT_SLICES`.
4. **`meet`: a pair budget per tick.** The grid is right; the crowd defeats it.

Doing 1 and 2 removes about 100 ms/s of work and, more to the point, removes the two longest lumps. Expected
result at 500 crowded: the loop p99 falls from 641 ms toward the 100-150 ms that `racialRegen` and the remaining
per-player timers imply, which is still over the 50 ms gate, which is why 3 matters.

## 8. Which tree was measured, and which was quoted

Found after the report was first written, and it belongs at the front of the method notes rather than buried.

**The line numbers above come from `origin/server` at `774f50fd`. The measurements come from the files the
sandbox runs, which are copied from this PC's live `server\` folder.** Those are not the same tree. Checked
file by file:

| file | 774f50fd vs the measured copy | effect on this report |
|---|---|---|
| `npcground.js` | **byte-identical** | none; lines 171-196 are exactly the code measured |
| `debugsnap.js` | **byte-identical** | none; `playerView` at 33-56 is exactly the code measured |
| `racial.js` | regen loop unchanged, numbering shifted | `regenTick` is at **375** in the measured copy, not 460 |
| `gearstrip.js` | measured copy is the pre-fix version | `every('gearStrip')` is at **204**, not 229; the 868 ms is that version's |

So no conclusion moves, and the two timers carrying the finding are the identical ones. But two citations point
at the pinned commit's numbering rather than the code under the instrument, which is the same mistake in kind as
reading a tree 319 commits behind - it was luck, not method, that the important files matched.

**`origin/server` also moved during the work**, from `774f50fd` to `1b1d6aba`, because another session fetched
into this shared clone. Anyone reading `debugsnap.js:33-56` against `origin/server` today sees the restructured
version written in response to this report, not the version profiled here. A report against a moving ref has to
pin the commit *and* say which tree the numbers came from; this one now does both.

## 9. Method notes

- The tick lines are the instrument; `mean` is per run and `runs` is per 60 s window, so `runs / 60 * mean` is the
  share of a second. Where a timer's `runs` is below its period's implied count, it was starved - read its demand
  from `period x mean`, not from the product.
- The spread runs are what separate crowding from population, and they are worth keeping in any future profile
  for exactly that reason. Population alone cannot distinguish a per-player loop from a pairwise one.
- Relay on and off differ by less than the run-to-run spread for every timer here, so none of this is affected by
  the C++ change under test.
