# Taking the bot harness past 100: 250, 500 and 1,000

PC load-test session, 2026-10-18. Task 3 of the 1,000-player work. Plan and costs only. Nothing here was run
against CT 115 or the live server, and nothing should be without Nat: every number below came from this PC's own
sandbox on port 7787.

## 1. What one bot costs, measured tonight

50 bots against the local sandbox, sampled every 5 s at steady state:

| | measured |
|---|---|
| host processes | 5 (`botsPerHost` 10) |
| bot-side memory | 184 MB total, **37 MB a host, 3.7 MB a bot** |
| bot-side CPU | 0.56 of a core for 50, **about 1.1% of a core a bot** |
| sandbox server | 1.75 GB RSS at 50 bots |
| each bot sends | 7.7 movements a second, the real client rate |

Each bot needs its own copy of `MpClientPlugin.dll` (1 MB) because the DLL keeps one client in file-static state, so
the copies scale with bots, not hosts.

## 2. What the targets cost, extrapolated from that

| target | host processes | bot RSS | bot CPU | DLL copies | connect ramp at `connectGapMs` 250 |
|---|---|---|---|---|---|
| 250 | 25 | ~0.9 GB | ~2.8 cores | 250 MB | 63 s |
| 500 | 50 | ~1.9 GB | ~5.6 cores | 500 MB | 125 s |
| 1,000 | 100 | ~3.7 GB | ~11 cores | 1 GB | 250 s |

This PC has 32 logical cores and 41 GB free, so the **bot side** of all three fits here. The server under test is the
question, and section 4 answers it.

## 3. Four ceilings, in the order they bite

**1. `MAX_PLAYERS=1000` is a compile-time constant.** `skymp5-server/cpp/CMakeLists.txt:46` sets it, `Config.h`
exposes it as `kMaxPlayers`, and `Networking.cpp:148` **throws** if `maxConnections` exceeds it. `ActorsMap` and
`ServerState` also size themselves to it. So 1,000 is the exact ceiling, not a target with headroom: a 1,000-bot run
leaves no slot for an observer, a staff account or a single real player. Testing at or beyond 1,000 needs that line
raised and a C++ rebuild, which is claude-jake's and the leader's, not mine. Worth noting too:
`skymp5-backend/.env.example` advertises `SERVER_MAX_PLAYERS=600`, so the backend's own cap needs checking before any
public attempt.

**2. The connect ramp is serialised by source IP.** RakNet's `SetLimitIPConnectionFrequency(true)` refuses a second
connection from one address inside about 100 ms; the harness paces at `connectGapMs` 250 to stay clear. From one
machine that is 100 s at the floor and 250 s as configured, for 1,000 bots. It is a ramp, not a wall, but a run has
to allow for it, and the step timings in a report must start after the last bot is in. More source addresses are the
only way to shorten it.

**3. The sandbox's own `maxPlayers`.** `lib/sandbox.js` writes 200. It has to rise to the step size, and it cannot
exceed ceiling 1.

**4. Bot CPU against server CPU on one machine.** At 1,000 the bots want ~11 cores. With today's quadratic relay the
server would want far more than it can get, so a local 1,000 run measures the two sides fighting rather than the
server's true limit. 250 and 500 are safe locally; 1,000 is not a local test.

## 4. Three ways to run it

**A. All on this PC (bots + sandbox).** Works today, no permission needed, no network variables. Good to 500. At
1,000 the bots and the server compete, and loopback hides the real wire. **Recommended for 250 and 500 now.**

**B. Bots here, sandbox on CT 115** - the alpha gate's option A, already written (`ALPHA-GATE.md`,
`ct115/sandbox.sh`). The build under test is exactly the live one and the server gets CT 115's cores to itself, but
every bot's traffic crosses Jake's uplink, and through the ssh tunnel ping and loss become the tunnel's rather than
the internet's. **Needs Nat, and Jake for the 100-step upload. Not to be run on anyone's say-so but theirs.**

**C. Bots on several machines against one sandbox.** The only arrangement that gives real wire behaviour and more
than one source IP, so the only honest way to measure 1,000. Needs hardware we do not have tonight.

The sequence that gets the most information for the least risk: **250 and 500 locally against today's build**, to
confirm the quadratic curve the design predicts and to fix the per-send cost on real hardware; then the same two
steps again once interest management lands, which is where the design's claims get tested; then 1,000 on option B or
C, after `MAX_PLAYERS` is raised.

## 5. What the harness needs built (all local, all mine)

1. **Two scenarios, reproducible.** The design is judged on "spread" and "crowded" and the harness only really does
   crowded today (`spread: "city"` puts every bot in one place). Add a spread mode that distributes bots across
   several worldspace cells at a configured separation, so both rows of the design's table can be measured rather
   than modelled.
2. **Per-emitter counting, which is the instrument interest management actually needs.** Count `UpdateMovement` per
   emitter per bot and bucket by distance at receipt. That gives, directly: the nearest 32 still at full rate, the
   mid tier at its rate, the far tier at its rate, and the tracked cap. Without it a ladder can only be judged by
   total traffic, which cannot tell a correct ladder from a broken one that drops the wrong actors.
3. **A bot-side sampler in the report.** I measured host RSS and CPU by hand tonight; the runner should record it per
   step, so "the harness is not free" becomes a number in every report instead of a caveat.
4. **Scale knobs.** `botsPerHost` higher than 10 (fewer processes, less per-process overhead), and `connectGapMs`
   settable per source so option C can pace per machine rather than globally.
5. **Steps and thresholds.** Reuse the alpha gate's `gate.json` with steps 250/500/1,000 and the pass criteria from
   `CAPACITY_PLAN.md`: loop lag p99 under 50 ms, per-client traffic under budget, no disconnects, memory flat.

## 6. What this plan deliberately does not do

- Nothing is run against CT 115 or the live server. The alpha gate's CT 115 path exists and is written down, and it
  stays unused until Nat says otherwise.
- No C++ is touched, including the one-line `MAX_PLAYERS` change, which belongs to the C++ owner.
- A 1,000-bot run against today's build is not scheduled, because it would measure the wall we already measured at
  100 and not the fix. The interesting 1,000 run is the one after interest management.
