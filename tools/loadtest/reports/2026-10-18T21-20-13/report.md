## How to read these numbers

- Directions are from the server: "to server" is what the bots send, "to bots" is the fan-out.
- **msg/s to bots (JSON KiB/s)** is measured at the bots after the native serializer turned each
  message back into JSON, so it is an upper bound on the wire payload: binary movement is
  smaller than its JSON form. Per-process network bytes are not available on Windows without
  ETW (measured: a 10 MB UDP loopback send moves Win32_Process WriteTransferCount by 0), so
  **UDP dgram/s** is the machine-wide `\UDPv4\Datagrams Sent/sec` counter, which does see
  loopback, minus the idle baseline. For a real bytes/s figure run the bots on a second machine
  and read the NIC counters, or capture with Wireshark.
- **tick** is `server.tick()` plus the `await setTimeout(1)` after it (index.ts:269), so p50 is
  the loop period and not the work: a p50 near 15-16 ms is the Windows timer granularity, not load.
- **loop lag p99** is the number to watch: it is what a player feels as delay.
- Bots do not run AI, so nothing they host fights back. Without `--host-npcs` an NPC near a bot
  is never driven by anybody, which means a bot-only run under-represents hosted-actor traffic.
